# P0 重构差异清单（对话模块 V2.0 · 第一阶段）

日期：2026-11-13
范围：只审查、不改代码。对应任务书“第一步：代码审查，输出差异清单”。

## 0. 审查范围与现状数据流

已读代码：
- 对话链路：`ChatController`、`ChatServiceImpl`、`ChatTurnVO`、`ChatSessionVO`、`ChatProfileDTO`、`AnchorStateDTO`、`ChatIntentRouter`、`ChatSpotRecommender`、`PromptLoader`、`chat-system.txt`
- 生成链路：`ItineraryGenerateServiceImpl`、`ItineraryConstraintEnforcer`、`ItineraryValidateServiceImpl`、`GenerateRequestDTO`、`ContextBuilder`
- 存储：`chat_session` 表（`context TEXT`）、`ChatSessionMapper`
- 前端：`ChatSidebar.vue`、`stores/explore.js`

现状数据流：
1. `POST /api/chat/message` → `ChatServiceImpl.send()`
2. 读 `chat_session.context` → 反序列化**裸 `ChatProfileDTO`**
3. 前端整份画像覆盖 → 意图分流 → 可选景点取数 → 调模型
4. 解析 `{reply, profile_patch, notes, action}` → 合并画像 → `finalizeProfile`
5. 把裸 `ChatProfileDTO` 序列化写回 `context`
6. 返回 `ChatTurnVO`（profile/missing/action/warnings/spots）
7. 生成：前端带 `GenerateRequestDTO`（含 avoid/mustVisit 文本）+ `sessionId` → `buildDialogBrief` 读 `context.notes` 和最近 4 条原话 → 拼 prompt → 模型生成 → `ItineraryConstraintEnforcer` 裁剪 → 落库 → `ItineraryValidateService` 做 POI/预算/时间重叠校验

结论：链路完整，但**“日期证据、跨字段一致性、约束执行”三层不存在**；“事实一致性/能力边界”只靠提示词自觉。

## 1. P0-1 日期依据与一致性

### D1 日期没有原话依据也能写入
- 位置：`ChatServiceImpl.mergeProfile`（762-775 日期、777-778 锚点）、`normalizeDate`（1001-1061）、`mergeAnchor`（818-867）
- 现状：模型 `profile_patch` 只要给出任意未来日期就接受；`normalizeDate` 只拒绝“过去日期”和“两年后”（1052-1059），“今天/未来任意日”全部放行；不记录来源文本，不要求 evidence。
- 实测：P3 T02 用户只说“下午5点坐高铁到成都东站”，写入 `arrival.date=2026-11-13`、`startDate=11-13`；泉州自玩第 12 轮用户只说“不想爬山”，`startDate` 被写成当天。
- 预期：日期必须能在本轮用户原话中找到依据；无依据不写入；模型不能补当前日期。
- 影响：READY 误判、行程日期错误、用户看到凭空出现的出发日。
- 修改方案：
  1. 合并前做“原话证据校验”：`patch` 中新增的每个日期值，必须能由本轮 `content` 的日期/相对日期规则推导出同一个值（复用 `DATE_*`、今天/明天/后天）。
  2. `source=chat` 且无证据 → 丢弃该字段并写 `warnings`；`source=form` 视为用户手填，直接接受。
  3. 禁止“无日期词却写入今天”，除非原话含今天/今晚/现在。
- 回归：`DATE-001` “我下午到泉州”→ `arrival.date=null`；`DATE-002` “我不想爬山”→ 日期不变。

### D2 模糊时间被转成精确时刻
- 位置：`normalizeTime`（1064-1113）、`AnchorStateDTO`（21-43，无 timePeriod）
- 现状：`下午/傍晚/晚上` 会 +12 转成 `HH:mm`；“下午到”若模型给 `time` 就落成 17:00。结构上**无法保存“下午”**。
- 实测：泉州第 11 轮“下午到”→ `arrival.time=17:00`，同一句还反问“几点到”。
- 预期：只存模糊时段（`timePeriod`），不生成精确时刻；只有原话出现“5点/17:00/五点半”才写 `time`。
- 影响：编造时刻，生成侧首日边界错误。
- 修改方案：`AnchorStateDTO` 增加 `timePeriod`（MORNING/AFTERNOON/EVENING/NIGHT/UNKNOWN）；`normalizeTime` 仅在原话含数字+点/冒号时产出 `HH:mm`；生成入参新增同一字段（可空，向后兼容）。
- 回归：`DATE-003` “下午到”→ `time=null,timePeriod=AFTERNOON`；`DATE-004` “晚上抵达”。

### D3 日期顺序不校验
- 位置：`finalizeProfile`（891-939，只比较 start/end）、`mergeAnchor`（818-867）
- 现状：`startDate=11-13`、`arrival.date=11-22`、`endDate=11-16` 可以同时存在；到达早于出发、晚于结束都不报错。实测 after 与 after2 均复现。
- 预期：`startDate ≤ arrival.date ≤ endDate`；冲突字段不参与 READY，并明确提示。
- 影响：行程自相矛盾；生成时首日边界与日期区间冲突。
- 修改方案：`finalizeProfile` 增加跨锚点校验；冲突时保留“用户最后一次明确说出的值”，清空派生值，写 `warnings`；把校验结果传给 `actionOf`。
- 回归：`DATE-005` 起止/到达冲突；`DATE-006` 同日到达时刻与出发时刻冲突。

### D4 换目的地后旧日期残留
- 位置：`mergeProfile` 换城市分支（716-721）
- 现状：`cityChanged` 只清 `arrival/departure/mustVisit`，不清 `startDate/endDate`。实测改去西安后仍沿用成都的 11-20~11-23，且当轮 `ready`。
- 预期：默认清空与旧目的地绑定的日期；用户明确“日期不变，只改城市”时保留。
- 影响：新城市沿用旧日期，READY 误判。
- 修改方案：换城市时判断本轮是否给出日期；未给出则清空 `startDate/endDate` 并进入待确认；给出则按新值写入。
- 回归：`DATE-007` 换城市清日期；`DATE-008` “日期不变，只把成都改成重庆”保留。

### D5 READY 只看字段非空
- 位置：`actionOf`（983-990）
- 现状：`city + (days 或起止区间) + (startDate 或 arrival.date)` 非空即 `ready`；不看证据、不看一致性、不看冲突。
- 影响：编造日期/矛盾日期也能触发 ready（实测第 12 轮）。
- 修改方案：`actionOf(ctx, profile, dateValidation)`；存在冲突或关键日期无证据 → 强制 `chat`。
- 回归：`READY-001` 无日期不 ready；`READY-002` 冲突日期不 ready。

## 2. P0-2 硬约束当轮落库并参与业务过滤

### C1 约束没有类型和状态
- 位置：`ChatProfileDTO`（44-52：`mustVisit`/`avoid`/`notes`）、`GenerateRequestDTO`（42-43）、前端 `chatProfile()`（552-579）
- 现状：约束全塞字符串数组；`notes` 与 `avoid` 语义重叠；无 `type/scope/active/sourceText`，无法区分“喜欢美食”和“海鲜过敏”。
- 修改方案：新增 `TravelConstraintDTO{content,type(PREFERENCE/EXCLUSION/SAFETY),scope,active,sourceText}`；`profile.constraints` 为主，`avoid/notes` 保留兼容；旧 `avoid` 迁移为 `EXCLUSION`。
- 回归：`CON-001` 海鲜过敏→SAFETY；`CON-002` 不爬山→EXCLUSION；`CON-003` 修改约束→active 更新。

### C2 约束当轮不落库
- 位置：`mergeProfile`（756-758）、`mergeNotes`（877-889）、模型输出处理（218-224）
- 现状：只有模型 `profile_patch` 主动给了 `avoid` 才写；`notes` 完全依赖模型。实测“海鲜过敏”第 6 轮无任何字段，直到第 14 轮才进 notes；P6“不吃辣/不购物店”当轮 notes 为 null。
- 修改方案：服务端加确定性兜底抽取（过敏/忌口/不吃/不能/不想/不安排/不购物 + 名词），与模型 patch 合并；当轮写入 `constraints`；无法归类才落到 notes。
- 回归：`CON-001` 断言当轮 `context.profile.constraints` 含 SAFETY 项。

### C3 景点推荐不过滤约束
- 位置：`ChatSpotRecommender.fetch`（115-151）、`wantsSpots`（106-109）、调用处 `ChatServiceImpl`（152-161）
- 现状：只做“有图/去重/评分”，不接收画像或约束；实测向海鲜过敏用户推荐“土笋冻”。
- 修改方案：`recommend(city, profile, constraints)`；过滤顺序：基础合法性 → 硬约束 → 安全约束 → 去重 → 评分；成分/属性无法判断时输出“请核实”，不得宣称安全。
- 回归：`CON-004` 过敏用户不出现海鲜类；`CON-005` 不爬山不出现登山类。

### C4 生成链路不执行约束
- 位置：`ItineraryGenerateServiceImpl.buildUserPrompt`（757-758，avoid 只拼文本）、`ItineraryConstraintEnforcer.enforce`（42-162，只查时间/节奏/住宿/去重）、`ItineraryValidateServiceImpl.validate`（40-136，只查 POI/预算/重叠）
- 现状：约束只是 prompt 文本；模型不听话就直接进最终行程；后校验没有约束检查。
- 修改方案：新增 `ConstraintValidator`，在 `enforce` 之后、落库之前执行；`EXCLUSION` 命中直接删除/回填；`SAFETY` 命中拦截，无法判定则标记“待核实”，不得标安全。
- 回归：`GEN-001` 不爬山行程无登山节点；`GEN-002` 过敏行程无明确海鲜菜；`GEN-003` 生成后校验被调用。

### C5 约束不能修改/取消
- 位置：`mergeProfile`（758 `normalizeList` 整体覆盖）
- 现状：只能整列表覆盖，无法表达“之前说不爬山，这次可以接受轻松山路”。
- 修改方案：按 `content` 归一识别同一约束，更新内容/`active`，保留 `sourceText`；模型协议支持 `constraints` 补丁。
- 回归：`CON-006`。

## 3. P0-3 事实一致性与能力边界

### F1 事实可被质疑翻转
- 位置：`chat-system.txt`（无相关规则）；实测泉州第 11/12 轮
- 现状：用户一句“你确定吗”，开元寺预约从“不用”翻转成“需要”，无核查、无不确定说明。
- 修改方案：Prompt 增加：已给出的事实不因质疑反转；无新证据时明确“不确定”；实时规则/价格/预约不作确定性承诺；没有查询结果不得声称已核实。
- 回归：`FACT-001` 同一事实连续两问，结论一致或明确不确定。

### F2 能力越界承诺
- 位置：`chat-system.txt`（有“越界拒绝”，无“能力边界”）；实测“帮你订酒店/查高铁”
- 修改方案：Prompt 明确能力表：可推荐/筛选，不可代订、不可查实时车次/余票、不可购票；给替代话术。服务端不做语义拦截，靠回归用例守。
- 回归：`CAP-001` “帮我直接订酒店+查高铁”必须明确说明做不到。

## 5. 与现有设计的冲突与影响

1. **`forbiddenAsk` 与 P1 策略层冲突**：P0 保留（避免回归），P1 删除，换成 `ConversationState.consecutiveQuestions`。
2. **`avoid/notes` 与 `constraints` 并存**：P0 双写（constraints 为主，avoid/notes 仅兼容与展示），P1 收敛后删除重复语义。
3. **改 `ChatServiceImpl` 主流程风险高**：当前没有对话单测；建议先落回归测试骨架（用 `MockLlmClient` 固定输出），再改主流程。
4. **`ItineraryConstraintEnforcer` 不应继续膨胀**：约束校验放独立 `ConstraintValidator`，与时间/节奏规则分开。
5. **生成链路耦合 prompt 文本**：P0 只加“生成后校验”，不改生成 prompt 结构，避免影响现有生成质量。

## 11. 实施状态（2026-11-13）

### 已完成

- **P0-1 日期**：`DateEvidence` 从原话提取日期/时刻/模糊时段，`ChatServiceImpl` 合并时拒绝无依据日期、模糊时间不转精确；`DateRules` 校验 `start ≤ arrival ≤ end` 与返程边界；换目的地清空旧起止日（明确“日期不变”除外）；`actionOf` 加入一致性门槛；被拒绝的日期从回复正文里清掉。
- **P0-2 约束**：`TravelConstraintDTO` + `ConstraintType`（PREFERENCE/EXCLUSION/SAFETY）；服务端当轮兜底抽取并与模型补丁合并、同类去重、支持 active=false 取消；`ChatSpotRecommender` 按约束过滤；生成后 `ConstraintValidator` 二次校验（海鲜/登山/购物）。
- **P0-3 事实与能力**：Prompt 增加“质疑不翻转、未查到不声称已核实、不代订/不查实时车次、过敏原不得保证安全、reply 不写用户没给的日期”。
- **P0-4 上下文**：`ChatContextDTO{version=2, profile, conversationState}`；旧裸画像惰性迁移（avoid → EXCLUSION），不虚构字段；`ChatTurnVO/ChatSessionVO` 返回 constraints 与 conversationState。
- **前端**：画像约束随对话与生成请求传递；`MISS_LABELS` 补 `lodgingMode/lodging`；会话状态仅接收不驱动 UI。
- **测试**：`src/test/java/com/xingji/chat/P0RulesTests.java`，13 条全通过。

### 端到端验证（真实后端 + 真实模型）

1. “下午5点坐高铁到泉州站” → `arrival.date` 不写入、`startDate=null`，回复中的“11月14日”被清为“日期待定”，并附“到达日期没找到依据”。
2. “她海鲜过敏，别安排海鲜” → 当轮写入 1 条 SAFETY（去重后），后续轮次不清空。
3. “她也不想爬山” → 新增 EXCLUSION，推荐景点时“清源山”被过滤。
4. “改去西安” → 起止日期清空、`action=chat`，回复不再沿用成都日期。
5. “帮我直接订好酒店，再查一下高铁” → 明确说明无法代订/查询。
6. context 写入 v2，`conversationState` 含 `lastIntent/currentTopic/consecutiveQuestions`。

### 已知问题（P1 或后续）

- 事实一致性目前只靠 Prompt，没有语义级“前后矛盾检测”；需要固定用例守。
- `scrubUnverifiedDates` 是正则清理，极端情况下可能误伤与行程无关的日期表述。
- 行程按天重排（`DayRegenerateDTO`）暂未携带 constraints。
- 约束过滤是关键词级；成分未知的餐饮只记日志，不宣称安全。
- `ConversationState` 只落库，不驱动策略（符合 P0 范围）。
- 注册空 email 500 未修（与本轮对话重构无关）。
