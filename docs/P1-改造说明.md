# P1 改造说明（自然对话与交互）

日期：2026-11-13
范围：对话模块 V2.0 第二批。P0 的正确性改造保持不变。

## 一、完成项

| 任务书要求 | 实现 |
|---|---|
| 取消 A/B 回答模式 | 提示词删除 A/B、固定字数、固定景点数和每轮强制追问；改为按上下文动态回复 |
| 建立意图分类 | `ChatIntent`：EXPLORE/PLAN/DISCUSS/MODIFY/CONFIRM/SMALL_TALK/OUT_OF_SCOPE/UNKNOWN；模型为主，服务端校验，非法回落 UNKNOWN |
| 画像与对话状态分离 | `ChatProfileDTO` 保留；新增 `ConversationStateDTO`，与 profile 一起存 `chat_session.context` v2 |
| 重构追问策略 | `ChatStrategyService`：ANSWER/SUGGEST/ASK/DISCUSS/CONFIRM/COMPLETE；连续追问≥2 次自动转 SUGGEST；不再使用 `forbiddenAsk` 硬禁 |
| 新模型协议 | `reply / intent / profile_patch / conversation_update / next_step`；服务端校验枚举与长度；**不再拼接多个 JSON 对象**，只取第一个有效对象 |
| 强化画像合并 | 用户本轮原话优先级、建议不自动落库（只来自 profile_patch）、P0 日期/城市/锚点清理逻辑保留 |
| 重构 action | 服务端 `ChatActionResolver`：CHAT / READY / GENERATE；信息齐全只给 READY，用户明确说“生成吧”才 GENERATE |
| 保留真实 POI | `ChatSpotRecommender` 保留约束过滤；寒暄/无关对话不触发 |
| 前端卡片 | 画像卡三态（已确认/待确定/已排除）；action=ready/generate 显示不同提示，不自动调用生成 |

## 二、协议变化

旧：
```json
{"reply":"...","profile_patch":{},"notes":[],"action":"chat"}
```

新：
```json
{
  "reply": "...",
  "intent": "PLAN",
  "profile_patch": {},
  "conversation_update": {
    "stage": "COLLECTING|DISCUSSING|READY",
    "currentTopic": "泉州旅行安排",
    "undecidedItems": [],
    "acceptedSuggestions": []
  },
  "next_step": "ANSWER|SUGGEST|ASK|DISCUSS|CONFIRM|COMPLETE"
}
```
`next_step` 只是建议；最终 `action` 由服务端按“画像完备 + 日期自洽 + 用户明确授权”计算。

## 三、策略规则（轻量，不做规则引擎）

- 画像已具备生成条件 → COMPLETE
- 用户在提问（问号/怎么/多少/推荐…）→ ANSWER
- 用户犹豫（随便/你定/还没定）→ SUGGEST
- 连续追问 ≥ 2 → SUGGEST（停止追问）
- 缺核心信息（city/days/startDate/arrival.date）→ ASK
- 其余 → DISCUSS

追问次数由服务端统计（`ConversationState.consecutiveQuestions`），不再靠提示词禁令。

## 四、action 判定

- `CHAT`：信息不全或日期冲突
- `READY`：城市 + 天数/日期区间 + 出发或到达日期，且日期自洽
- `GENERATE`：在 READY 基础上，用户原话明确说“生成吧/按这个生成/开始排”等；否定（“先别生成”）仍为 CHAT

模型不能直接让后端执行生成；前端看到 `generate` 只高亮按钮，不自动请求。

## 五、前端

- 画像卡三态：已确认（城市/天数/出发日/预算/人数/偏好/必去）、待确定（服务端 missing）、已排除（EXCLUSION/SAFETY 约束）。
- `action=ready`：提示“信息够了，确认后可生成”；`action=generate`：提示“你已确认生成，点按钮开始”，按钮文案变为“开始生成行程”。
- 约束随对话回传并进入生成请求；`lodgingMode/lodging` 中文映射补齐。
- 对话请求超时从 45s 提到 120s（浏览器实测 45s 会被真实模型延迟打穿，后端已落库但前端报错）。

## 六、验证

- `P0RulesTests` 13 条 + `P1StrategyTests` 13 条，共 **26 条全部通过**。
- 后端 `mvn package` 通过；前端 `vite build` 通过。
- 真实后端 + 真实模型验收：
  - “我想去泉州玩三天” → intent=PLAN、strategy=ASK、只问一个问题。
  - “泉州有什么好吃的？” → intent=DISCUSS、strategy=ANSWER、直接给内容、不强行追问。
  - “随便你定” → strategy=SUGGEST、给默认建议。
  - 补齐日期 → action=ready；说“就按这个生成吧” → action=generate。
  - 约束（海鲜过敏/不爬山）当轮落库，景点卡片过滤清源山。
- 浏览器验收：登录 → 探索页 → 打开旅行画像，三态卡片正常渲染（已确认：目的地泉州 · 3 天 · 预算 2000；待确定：无）。

## 七、已知问题

- **回归用例数量**：当前 26 条是规则级用例；任务书要求的 30 条“完整对话用例”需要固定模型输出/回放，尚未补齐。
- **超时语义**：前端超时只提示失败，后端可能已经落库；重发有重复消息风险，后续可加请求幂等键。
- **模型仍可能建议日期**：服务端会清理未获证据的日期，但回复可能出现“日期待定（周日）”这类不自然表述。
- **意图/策略依赖模型质量**：GLM-4.5-Flash 偶尔返回非法 next_step，服务端回落计算策略；命中率需继续用回归集观察。
- **约束过滤是关键词级**：成分未知的餐饮只记日志，不宣称安全。
- **按天重排**（`DayRegenerateDTO`）尚未携带 constraints。
- **ConversationState 只落库**：策略用的是连续追问/缺失项，acceptedSuggestions/undecidedItems 还没参与决策。
